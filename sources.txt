API Integration Guide — Approved Source Architecture

Product: Signal Map
Last updated: v2 consolidated guide

## 1. Purpose

This document defines the approved source integration strategy for Signal Map.

Signal Map is a public-first, personalized signal intelligence product that synthesizes:
- prediction markets
- forecasting platforms
- official government/political data
- macroeconomic data
- hazard/disaster feeds
- news/event evidence
- subject/reference metadata

into normalized topic pages showing:
- current picture
- what changed
- what signals currently point to
- what to watch next

This document is for engineering, data, and product teams deciding:
- which sources to integrate
- what role each source plays
- what cadence each source uses
- what is in-scope for MVP
- what should never be treated as a foundation

---

## 2. Source Strategy Principles

### Principle 1 — Not all sources do the same job
Every source must be assigned one or more explicit roles:

- **Signal source** — may affect deterministic scoring and topic state
- **Reference truth source** — anchors official facts, metadata, identifiers, or state changes
- **Evidence source** — explains what changed, but should not usually drive score directly
- **Watch-next / alert source** — useful for triggering freshness or upcoming-event hints

### Principle 2 — Public topic pages must not depend on live third-party calls
All sources feed worker pipelines. Topic pages only read internal normalized and snapshot tables.

### Principle 3 — Prefer official + structured + stable sources first
Priority order:
1. Official APIs / official feeds
2. Well-documented structured public APIs
3. Reliable RSS / structured datasets
4. Controlled scraping fallback only when truly necessary

### Principle 4 — No brittle social/platform dependency for MVP
Avoid building the MVP on:
- X/Twitter
- Reddit
- unstable unofficial Google News or platform scraping
- aggressive anti-bot targets
- unclear commercial-rights sources

### Principle 5 — Source-specific cadence matters
Do not use one global refresh interval. Cadence must reflect actual source freshness and cost.

## 4. Approved Source Stack by Priority

## 4.1 P0 — Launch Sources

### 4.1.1 Polymarket
**Role**
- signal source
- topic heat source
- geopolitics/politics expectation layer

**Best for**
- geopolitics
- conflict/war
- global politics
- public-interest long-tail topics
- some entertainment/pop-culture later

**Read surfaces**
- Gamma API for events/markets/categories
- public market/event metadata
- optionally CLOB/Data later if needed

**Use in MVP**
- REST polling only
- websocket later if justified

**Cadence**
- tracked markets: every 5 minutes
- market discovery polling: slower, e.g. every 15–30 minutes

**Key fields**
- market/event IDs
- title/question
- category/tags
- prices
- volume
- close time
- active/inactive/resolved status

**Rules**
- low-liquidity/noisy markets must be filtered before scoring
- market phrasing must be normalized aggressively into topics

**Scoring usage**
- yes, weighted expectation signal

**Evidence usage**
- possibly as source references in advanced evidence drawers later

**Operational notes**
- treat metadata and prices separately if needed
- use minimum liquidity/volume threshold before contributing materially

---

### 4.1.2 Kalshi
**Role**
- signal source
- structured event-market backbone for US politics, macro, weather/disaster

**Best for**
- US politics
- macro
- rates/inflation expectations
- disasters/weather event framing
- election event markets

**Use in MVP**
- REST polling first
- websocket later only for hotter/premium views

**Cadence**
- tracked markets: every 5 minutes

**Key fields**
- ticker/event ID
- market metadata
- yes/no prices
- volume/liquidity
- market status
- timestamps/history where available

**Scoring usage**
- yes, high-trust structured expectation signal

**Operational notes**
- one of the cleanest MVP integrations
- keep as first-class signal source

---

### 4.1.3 Metaculus
**Role**
- signal source
- long-horizon forecast layer
- watch-next enrichment

**Best for**
- geopolitics
- AI / science later
- medium/long-term “what next” context

**Use in MVP**
- hourly polling
- no need for high-frequency refresh

**Cadence**
- hourly

**Key fields**
- question ID/title
- resolution criteria
- status
- aggregate forecast
- timestamps/history if available

**Scoring usage**
- yes, but lower-frequency/longer-horizon weighting

**Operational notes**
- do not treat it like a fast live ticker
- ideal for expectation comparison and outlook

---

**Key fields**
- bill IDs
- action timestamps
- status changes
- committees

- documents/links

**Scoring usage**

**Operational notes**

### 4.1.10 One Strong News API (Bing News or equivalent)
**Role**
- evidence source only by default

**Best for**
- contextual headlines/snippets
- evidence drawer
- “what changed” support

**Cadence**
- every 15 minutes for hot topics
- slower for cold topics

**Rules**
- do not treat as direct scoring input by default
- store metadata and snippet carefully under terms

**Operational notes**
- choose one reliable provider instead of many weak ones for MVP

---

### 4.1.11 RSS Aggregator
**Role**
- evidence source

**Best for**
- curated sources
- official bulletins
- publisher feeds where stable

**Cadence**
- every 15 minutes for hot feeds
- source-specific otherwise

**Operational notes**
- good complement to commercial news API
- use only curated/high-value feed set

---

### 4.1.12 ReliefWeb
**Role**
- evidence source
- geopolitics/humanitarian context layer

**Best for**
- conflict zones
- humanitarian crises
- disaster/aid contexts

**Cadence**
- hourly or source-appropriate

**Operational notes**
- extremely valuable for geopolitics-heavy launch

---

### 4.1.13 GDELT
**Role**
- evidence source
- event-detection / subject heat source
- optional secondary scoring support later

**Best for**
- global event detection
- protest/conflict/political event heat
- multilingual coverage
- subject emergence/context

**Cadence**
- 15 minutes if used operationally

**Operational notes**
- very valuable
- noisy unless filtered carefully
- should start as evidence/event-detection layer before becoming a core scoring source

---

### 4.1.14 Wikidata
**Role**
- reference truth source
- entity spine

**Best for**
- canonical entities
- aliases
- linking people/countries/organizations
- metadata normalization

**Cadence**
- seed + periodic refresh
- not high-frequency

**Operational notes**
- should be part of topic seeding and canonicalization strategy

## 7. Ingestion Cadence Table

| Source Family | Approved Sources | Cadence | Primary Role |
|---|---|---:|---|
| Prediction markets | Kalshi, Polymarket | Every 5 min | signal |
| Forecasting | Metaculus | Hourly | signal / watch-next |
| News evidence | One news API, RSS | Every 15 min for hot topics | evidence |
| Political official data | Congress.gov, GovInfo, FEC | Intraday / daily | reference truth + signal |
| Macro official stats | FRED, later BLS/EIA | Release-based / daily | signal + reference truth |
| Hazard/weather | USGS, NOAA/NWS, Open-Meteo | 5–15 min | signal + alert |
| Humanitarian/conflict | ReliefWeb, GDELT, later HDX/UCDP | 15 min to daily | evidence / event heat |
| Reference entities | Wikidata | Seed + periodic refresh | reference truth |

## 8. Adapter Requirements

Every source adapter must declare:

- `source_key`
- `source_family`
- `role_types` (signal/reference/evidence/watch-next)
- `auth_model`
- `cadence_seconds`
- `license_class`
- `risk_level`
- `raw_payload_policy`
- `scoring_eligible`
- `evidence_eligible`
- `entity_linking_strategy`
- `rate_limit_policy`

Every adapter must also implement:
- fetch
- normalize
- dedupe/upsert
- health update
- provenance record
- retry-safe failure semantics

## 9. Normalized Model Mapping

### Observation
Atomic normalized input record from any source.

Fields:
- `observation_id`
- `source_name`
- `external_id`
- `payload_type`
- `occurred_at`
- `normalized_payload`
- `content_hash`
- `source_provenance`

### Subject
Canonical user-facing topic.

Fields:
- `subject_id`
- `canonical_name`
- `slug`
- `category`
- `aliases`
- `entity_refs`
- `status`
- `seeded_flag`

### Signal
Structured score-driving input.

Fields:
- `signal_id`
- `subject_id`
- `source_family`
- `source_name`
- `signal_type`
- `metric_type`
- `current_value`
- `previous_value`
- `delta`
- `confidence_modifier`
- `freshness`
- `weight`
- `last_updated_at`

### Evidence
Context supporting explanation.

Fields:
- `evidence_id`
- `subject_id`
- `source_name`
- `evidence_type`
- `headline_or_title`
- `snippet`
- `url`
- `published_at`
- `matched_entities`
- `relevance_score`

### Provenance
Auditability and source trace.

Fields:
- `provenance_id`
- `source_name`
- `endpoint`
- `query_params`
- `fetched_at`
- `license_class`
- `terms_notes`
- `adapter_version`
- `payload_storage_path`

## 11. Engineering Rules

### Rule 1
No source writes user-facing prose directly.

### Rule 2
Only approved signal sources affect scoring by default.

### Rule 3
Weak/noisy sources must have conservative weights and thresholds.

### Rule 4
All raw payloads go to object storage when retained.
Postgres stores metadata, hashes, paths, normalized forms, and provenance.

### Rule 5
Topic seeding is mandatory at launch.

### Rule 6
Source outages must surface as freshness/staleness changes, not silent failures.

### Rule 7
Adapters must be replaceable. Assume some APIs will degrade or die over time.
